### 8.3.1 symptom / pitfall 重复 —— 已按根因收敛（2026-10-08 定案并执行）

**这一节原先停在"两个方向都需要人拍板"，现已拍板并做完。** 下面先留档当时的
误判与更正，再写最终形态 —— 免得下次有人翻到旧结论又纠结一遍。

#### 当时的误判（保留，作为教训）

原先只按段落匹配估成"50% 重复"，进而推断"删掉一半正文"。**实测推翻**：

- 整节逐字相同：**0节**（不是"有24 节"）

  所以"症状页没瘦身"，代价不是体积而是**同一段解释写两遍、改一处漏一处就自相矛盾**。

误判根源：**只比段落、不比代码块，且没区分「复制」与「改写」**。
`§43.1` 两边看着完全不同，其实 symptom 侧那段是独立写的判别实验 —— 真内容。

> **踩过的坑（都写进脚本注释了）**：
> - 两族标题写法不同（pitfall `## 12.` vs symptom `### §12`），只认一种会测出 0 节。
> - `###症状` 这类**无编号子标题**不能把编号重置为 None，否则正文被判成空。
> - **不要靠"下一节标题的行号"定位插入点** —— 多次插入后行号会漂，
>   链接会跑到下一节标题之后。正确做法是扫出每节真实末尾（最后一行非空、
>   非尾注的行）再从后往前插。
> - 区分"已收敛"与"保留正文"**不能只看有没有根因链接**（两者都有），
>   要看「除链接外还有没有正文」。

### 8.4 上面那条「不能自动做」的结论，有一半是错的（更正）

`build_transition_table.py` 当初被我判为"不能拆"，理由写在上面 §8.3 的 ②：
*"搬完 3000 行只验得了一半的路径，验不全的重构不能自动做。"*

**那个理由说对了一件事，说错了一件事**，值得留档：

- ✅ **对**：那段代码的**探测流水线**（deck → PowerPoint 渲染 → 分析帧）
  确实要真 PowerPoint，本机跑不通。
- ❌ **错**：把"跑不通流水线"当成了"验不了搬家"。**这次做的是纯搬运** ——
  把整块函数从 A 文件挪到 B 文件，**行为按构造不变**。需要验证的不是流水线，
  是**模块结构**：import 能否解析、名字全不全、CLI 分发对不对、测试过不过。
  **这四件本地全能验。**

**实际拆完的验证（全部本地通过）**：

| 检查 | 结果 |
| --- | --- |
| 顶层名字（拆前 AST 扫出 vs 拆后可导入） | **64 / 64** 一致 |
| 逐符号原文比对（拆前 `git show` vs 拆后） | **64 / 64 逐字节相同**，无增无减 |
| CLI 子命令（写在 `facts/` 与 `reference/` 里的） | **19 / 19** 全在 |
| 测试套件 | 全绿；`check_structure` **0 FAIL** |

**但确实有一类真实风险，而且被抓到了**：
**代码依赖自身位置时，搬运会改变行为。** 实测撞了一次 ——
`decks.py` 里用 `os.path.dirname(__file__)` 拼 `motion_catalog.json`，
在原单文件里它恰好住在 `scripts/` 下所以是对的；搬进 `transition_probe/`
之后，**同一个表达式指向了一个不存在的地方**。

- 已改用 `common.SCRIPTS_DIR`（明确指 `scripts/`，不随模块位置漂）。
- ⚠️ **这类错静态检查完全看不见**，只能靠跑测试。所以：
  **搬代码前先 grep `__file__` 与相对路径拼装** —— 这是纯搬运唯一的真陷阱。

> **"纯搬运是安全的"这个判断，95% 成立。剩下 5% 就是这一条。**
> 它不会让搬运变得不值得做，但它意味着**搬完必须跑测试**，不能只看 import 通不通。

#### 8.5.2 这一轮踩的坑（都是「度量工具自己错了」）

**这一轮的失败全部出在度量脚本上**，不是被测对象上。四次连着来：

| 坑 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 依赖表全显示"叶子" | 一张把所有依赖都显示成没有依赖的表 | 在 `gen_code_tables.py` 里**重写了一份简化的 import 解析**，`import motion`认不出是 `scripts.motion` | 让 `scan_deps.py` 暴露 `build_graph()` 供复用。**依赖解析只许有一份** |
| 拆分脚本自我覆盖 | 第一次成功、第二次切出乱码 | 拆分器**读磁盘上的源**，而那正是它的输出 | 改从 `git show HEAD:` 取源 |
| 缩进校验拦下错切 | docs 段混进了收尾代码 | 上界行号少算一行 | 保留那道校验——**它拦住了一次静默的错切** |

> **这四条印证了 `CONTRIBUTING.md` §十.4：机器判据只用于报告，不用于自动改文件，

#### 8.5.4 做这两项检查时，又踩了一次「判据自己错了」

做 `check_reachability()` 时它**静默漏掉了本轮自己新建的两个工具**
（`split_tests.py`、`archive_handover_85.py`）—— 因为判据「文件被登记进索引了吗」
**依赖索引本身完整**。索引没写它，就等于它不存在。

**这是自己检查自己的盲区。** 修法：加一条**不依赖索引**的判据 ——
直接对比「磁盘上 `tools/` 真实有哪些 `.py`」vs「四份子索引里提到了哪些」。
加上之后立刻抓出 **8 个漏登记**的脚本（原来只登记了 4 个拆分器）。

> **教训：判据依赖某份数据时，那份数据本身也要被独立校验。**
> 否则检查和被检查的对象共享同一个盲区，**一起错，而且看起来全绿**。

同一轮还修了一个假阳性：`index-stale` 把 `tools/scan_deps.py` 报成
`tools/scan_deps.ps1`（不存在）—— 试两种扩展名时**试完 `.py` 没 `break`**，
循环结束留下最后一次的结果。**报「有问题」比不报更坏：假阳性会让人养成忽略它的习惯。**

**四项检查全部用负样本验证过**（造一个孤立 `.py`、一个没登记的 `tools/` 脚本，
确认能被报出来，然后删掉）。

> **「0 条违规」有两种可能 —— 真的干净，或者判据写错了。**
> **分不清这两者，就不能相信这个 0。** 这是本项目 §十.4 那条规则最实际的体现。
