## 43. 切换的机制：**写在哪一页、能装几个、时长听谁的**

<a id="s1"></a>

前两节解决的是"名字对不对"。这一节解决的是"用起来的三件事"，
它们都是**渲染出来的帧**给的答案 —— **读 XML 一分都分不出来**。

### 43.1 `<p:transition>` 挂在终点页上

两种互斥的说法：**A** = 写在第 N 页就动「进入第 N 页」（N-1 → N）；
**非 A** = 动「离开第 N 页」（N → N+1）。两种说法下"切换在第 N 页上"都成立，
所以看 XML 什么都证明不了。

判别用的 deck：**三页，只有第 2 页写 `<p:push dir="u"/>` 800 ms**，导出视频数帧。

```text
anchor.mp4（30fps，每页停留 2s）
62–85    24帧 = 800ms   过渡 burst   边界 1（第1页→第2页）
148–148   1帧 =  33ms   硬切         边界 2（第2页→第3页）
```

burst 落在**进入第 2 页**那一次。**非 A 被排除。**

- **推论**：写错页 = 效果往前挪一个边界。想在 5→6 页动画化却写在第 5 页，
  得到的是 5→6 硬切、4→5 意外动起来。决定这个位置的是 spec 的 `slides[].page`
  —— **它是终点页，不是出发页**。
- **第 1 页没有前驱**，它的切换只用在**放映起步从黑场进入开场**那一次，
  不是"被忽略"。实测第 1 页的 `<p:wipe dir="l"/>` 800ms 渲染出了 767ms 的真 wipe
  （逐列灰度显示边界自右向左推进），此后真正的第 1→2 边界是单帧硬切。

这也解释了 §20.4 那条"两页都要加 morph"：第 2 页的 morph 管"进入第 2 页"，
第 1 页那个管"第 1 页自己被进入"，同一条链上的两段。

### 43.2 一个 `<p:transition>` 只有一个子元素槽位

```text
twochild.pptx      <p:push dir="u"/> + <p159:morph option="byObject"/>  -> 拒开整份
twochild_core.pptx <p:push dir="u"/> + <p:wipe dir="l"/>                -> 拒开整份
```

不是丢一个、不是留第一个，是**整份文件打不开** —— 与 §42 那五个缺 `dir` 同一类失败。
之所以要同时验证 core+core 与 core+扩展两组，是为了排除"p159 特有"这种解释。

**因此**：「形状形变」与「整页位移」抢同一个名额，二者不可同时表达；
页内的个体行为必须走 `<p:timing>`，**两者在"能装几个"上互不占用**
（但它**不是**时间上正交 —— 页内动画排在切换之后，见 §51）。

### 43.3 时长听毫秒的，但 Fallback 里没有毫秒

`<p:transition>` 上有 `spd`（三档）和 `p14:dur`（毫秒）两个都像时长的东西。
让它俩打架：

| 写进去的 | 若 `p14:dur` 赢 | 若 `spd` 赢 | 实测 burst |
| --- | --- | --- | --- |
| `spd="slow"` + `p14:dur="200"` | ~60 帧 | ~6 帧 | **6 帧 = 200 ms** |
| `spd="fast"` + `p14:dur="1500"` | ~15 帧 | ~45 帧 | **44 帧 = 1467 ms** |

**`p14:dur` 赢。** 但 `mc:Fallback` 里**不可能有** `p14:dur`（那是 2010 的属性，
而 Fallback 的世界正是没有 2010 扩展的那个世界），所以 WPS / 旧版 / 在线预览
**只认 `spd`**。于是"快中慢"值多少毫秒必须量（同一 `<p:dissolve/>`，不写 `p14:dur`）：

```text
slow  30帧 = 1000ms      med  22–23帧 = 733/767ms      fast  14–15帧 = 467/500ms
```

（不是界面上传说的 3s/2s/1s。）每组都做了**每页停留 2s 与 5s 两次**，数字不变。

**还有一条只看往返会误判的**：PowerPoint 会把 `mc:Choice` 里的 `spd` 按它自己的
粒度重算 —— 写 `spd="med" p14:dur="800"`，存回来是 `spd="slow"`、`p14:dur` 仍是
`800`。**毫秒没动，动的是那个粗档位**；用 COM 读 `SlideShowTransition.Duration`
得到 0.8s，与写入一致。所以"往返后 spd 变了"不等于"时长丢了"。

**代码后果**：`build_transition` 原先把非 morph 的 `spd` 写死成 `"med"`、
并且静默忽略 `speed=`。于是 Choice 分支精确到毫秒，Fallback 却一律塌回 ~767ms。
现在 `spd` 由 `duration` 就近取档（≤633→fast，634–883→med，≥884→slow），
显式 `speed=` 也被尊重。

**同一处还有一个只在给 `advTm` 时才发作的 bug**：附加属性先贴到块上、再跑
`.format()`，最后一个 `{spd}` 就落进了贴过的那一半，写出 `spd="{spd}"` 这种半成品。
PowerPoint **照开不误**（按自己的规则改成 `slow`，`p14:dur` 留着），
所以除了往返比对，没有任何检查能发现。修法是附加属性与占位符一起合流，
并让两个分支都拿到它 —— 自动换页在 fallback 世界里同样要生效。

两条都由 `tests/test_transition_table.py` 钉住。

### 43.4 位置决定了它看不见形状

`<p:sld>` 是 `<xsd:sequence>(cSld, clrMapOvr?, transition?, timing?, extLst?)`：
`<p:transition>` 与形状容器 `<p:cSld>` **平级**，在容器之外。
它天生只能陈述"整页被怎样替换掉"，不能陈述"某个形状怎么动"。

### 43.5 ⚠️ 别用整帧均值判断过渡

同一个坑在本工程踩了两次：

1. **漏检** —— `dur="1500"` 的 wipe 逐帧只移动一条边，整帧 `absdiff` 均值只有 ~4
   （阈值 6），**1.5 秒的过渡被判成"没变化"**。
2. **误读** —— 第 1 页那段 wipe 的整帧均值平滑上升，**看起来完全像淡入**；
   看逐列灰度才发现是带方向的移动边界。

探测 deck 是纯色满幅背景，用"整帧平均色变没变"既灵敏又不受编码器噪声影响；
但要判断是**哪种**运动，必须看**空间剖面**（逐列 / 逐行 / 分块）。

机制层的完整论述见 [`transition-model.md`](transition-model.md)；
数据表见 [`transitions.md`](transitions.md)。

## 44. 切换的**形态**：观众看到的是什么运动

<a id="s2"></a>

`§40–§42` 解决"名字对不对"，`§43` 解决"机制怎么运作"，**都还没回答"看起来在做什么"**。
本节是形态层 —— 48 个效果各自是什么运动。完整对照表与复现步骤见
[`transition-shapes.md`](transition-shapes.md)，这里只记**踩过的坑**，
因为这一层的坑比前两层都多，而且每一个都是"能跑但测错"。

### 44.1 探测 deck 每格都变色 → 方向被平均掉

第一版探测 deck 让两页的网格**每一格都改色**，以为"差异越多越好测"。
结果差异图近似均匀，**`push`（最典型的整页位移）被测成"无方向"**。

修法：网格两页**完全相同**，当静态参照系；只让**一个标记**在两页之间移动 + 变色。

**教训**：探测画面要"只有一个变量在动"。让每一处都变，等于什么都没测到。

### 44.2 编码器噪声被当成过渡

H.264 在**本该完全相同的**帧之间留下孤立噪声尖峰。静止网格上实测：单帧能量 84–170。
而弱过渡的峰值可能只有 ~800 —— **峰值的 10% = 80，正落在噪声带里**。

后果：`wipe` / `fade` 的"活跃窗口"被撑到 **120 帧**（整个停留时长）。

修法：先按显著性取阈，**再要求连续性** —— 真实过渡是**连续的一段**，噪声是**孤立单帧**。
只保留 ≥3 帧的连续段。修完 `wipe` 从 120 帧收敛到 15 帧，`cut` 正确变成 0 帧。

**注意**：这里不能用 median+MAD 求噪声地板 —— 大多数帧**逐像素相同**时
median=0、MAD=0，地板算出来是 0，等于没有。

### 44.3 `random` 测不了，因为它自己就是随机的

`random` 两次探测给出不同结果。核对 XML：`clock` 写 `<p:wheel spokes="1"/>`，
`random` 写 `<p:random/>`；两个 mp4 **大小完全相同（186,629 字节）但 md5 不同**。

`<p:random/>` 每次放映随机挑一个效果，所以"`random` 的形态"**没有稳定答案**。
**实践含义**：用 `random` 无法保证任何观感一致性，商务场合不要用。

### 44.4 ⚠️ 一个探测 deck **分不开全部效果**

修完上面三个坑后，这些效果的径向剖面仍然**几乎完全一样**：

```
fade      [1.0, 0.15, 0.05, 0.11, 0.04, 0.0, 0.0]
wipe      [1.0, 0.15, 0.05, 0.12, 0.04, 0.0, 0.0]
dissolve  [1.0, 0.15, 0.05, 0.11, 0.04, 0.0, 0.0]
```

根因：deck 1 里两页之间**只有中心的圆在变**，不论什么效果差异都集中在中心。
它们的差别在**变化怎么扩散**，不在**变化在哪里**。

修法：**第二个探测 deck**（`shapedeck2`），两页都是**满屏随机噪点**（平均亮度相同、
空间图案不同）。于是：

| 效果 | deck2 上的表现 | 判据 |
| --- | --- | --- |
| `wipe` | 前沿逐区暴露新纹理 → 差异成**移动的带** | `band_travel` = −0.747 |
| `fade` | 整幅同时变化 → 差异**均匀** | `band_travel` = 0.015 |
| `push` | 整页滑走 → 差异**铺满全屏** | `coverage` = 0.957 |

**没有一个探测 deck 能同时看清所有效果。**
想知道"变化在哪"和想知道"变化怎么扩散"，需要**两种不同的画**。
`DECK2_SPECS` 那份 12 个效果的名单是**聚类**的产物，不是猜的。

### 44.5 别用首尾两帧做相位相关

对滑入类效果，过渡窗口的**首尾两帧都是"运动中途"的样子，互相很像**
→ 净位移读成 0。实测 `push` 首尾对比得 0，**逐帧累加**得 −4~−5px/帧，
方向与总位移都对。

### 44.6 别把"我测不出来"写成"它没有方向"

`honeycomb` / `shred` / `doors` / `window` 的位移指标是**小幅噪声级**
（不是 `push` 那种稳定的 −4~−5px/帧）。它们真实的样子是**内部纹理在变**，
既不是平移也不是均匀淡变。**对这四个本层给不出可靠方向结论** ——
如实标注"方向不可靠"，比硬填一个方向诚实。

### 44.7 测试通过 ≠ 测试有效

分析器的标定测试（合成帧序列：左推进必须判 `l->r`、右推进必须判 `r->l`、静止必须判 `none`）
**第一版自己是错的**：两个分支生成的帧**完全相同**（都是"白色从左边长出来"），
于是左右都判 `l->r` —— 而我把期望值也写反了，**测试"通过"了**。

直到把右侧分支改成"白色从右边长出来"，测试立刻报 FAIL，才发现分析器没问题、**测试有问题**。

**教训**：造标定样本时，先确认"两个样本真的不同"。同构的输入会让恒等映射也通过。

## 46. 证明"运动"不能用静态帧 —— 抽帧再多也证明不了方向

<a id="s3"></a>

### 46.1 症状：交了一份"看不到动效"的 PPT

用户原话：**"你给的 ppt 压根是静态的，看不到动效。"**

第一版证据 deck 每页贴 6 张**抽帧**（等间隔采样过渡区间）。我当时的想法是
"左→右就是时间先后，人眼扫一遍就知道方向"。**这是错的**：

> 抽帧能证明的是"某一刻画面上有什么"，
> 证明不了"它是怎么动的"。而形态层判的恰恰是**运动**。

一张 wipe 的 6 张抽帧，和一张 fade 的 6 张抽帧，在静态下看起来可以**完全一样**
（都是"画面在变"）—— 用户根本没法定夺方向对不对。**证据的形式必须匹配被证明的命题。**

### 46.2 做法：嵌入循环 GIF

pptx 里存 `ppt/media/image1.**gif**`（不是 png），PowerPoint 会**真的播**。

```python
s.shapes.add_picture("wipe.gif", ...)   # python-pptx 原样嵌入，不转码
```

复现要点：
- `ffmpeg -ss <起> -t <时长> -i in.mp4 -vf "<滤镜>" -loop 0 out.gif`
- **滤镜必须用调色板两遍法**，否则色带会把运动糊掉：
  `fps=15,scale=640:-1:flags=lanczos,split[s0][s1];[s0]palettegen=max_colors=128[p];[s1][p]paletteuse=dither=bayer:bayer_scale=3`
- `imageio_ffmpeg.get_ffmpeg_exe()` 拿到自带 ffmpeg，不要求系统预装。
- 校验：`zipfile` 看 media 里全是 `.gif`；`PIL.ImageSequence` 数帧数与 `loop`。

### 46.3 ⚠️ 帧数多 ≠ 看得见运动 —— 这才是真坑

改成 GIF 后我以为完事，结果量化一测：

| 效果 | deck1 帧间差异 | 肉眼 |
|---|---|---|
| push / pan | **38 / 39** | 清楚 |
| wipe / fade / split / random | **0.17 ~ 0.23** | **等于静止** |

GIF 有 21 帧、无限循环、结构完全合法 —— **但画面根本没在动**。
原因不在 GIF，在**探测 deck**：deck1 两页网格完全相同、只有一个小圆盘在动，
所以「整页平移」类看得清清楚楚，而「扫描/淡变」类几乎不改变任何像素。

**解法**：这四个效果换 deck2（全帧随机噪声，每个像素都在变），差异升到 **3.2**（15 倍）。

**结论**：效果和探测 deck 有配对关系 —— 不是随便哪个 deck 都能看出任意效果。
把命名清单写死（`DECK2_ONLY`），并加 `MIN_VISIBLE` 阈值自动拦截
"有帧数但看不出运动"的动画。**能自动检查的指标，不要靠人眼兜底。**

### 46.4 硬切是例外：低差异不是缺陷

`cut` 的帧间差异天然接近 0（0.17）—— 因为**它本来就没有中间态**，
这正是"硬切无过程"的形态特征。所以可见性检查要放行硬切，

## 47. 指标有盲区，而且盲区是"静默"的 —— 旋转从三个指标里漏过去了

### 47.1 症状：用户目视发现 `clock` 被判错了族

用户看完证据 deck 后说：

> `random` 的效果是，从 y 轴开始，顺时针一条线扫过全图，最后回到 y 轴。

一查，他看的确实是 `random`，但那次**抽中的是 wheel**（见 §三之补）。不过更要命的是：
文档里 `clock` 当时被归到**「中心扩散」**，方向记成 `t→b` —— **两条都是错的**。

### 47.2 根因：三类指标对旋转全都不敏感

| 指标 | 对旋转的反应 | 为什么 |
| --- | --- | --- |
| 变化漂移 | 原地打转 | 一圈扫下来差异重心回到原点，均值≈画面中心 |
| 累积位移 | 读不到 | 不是整页平移 |
| 径向剖面 | **撞车** | 旋转的径向分布和中心扩散几乎一样，都从中心向外 |

**前两类是"没反应"，第三类是"给了一个错的答案"。** 第三种更危险 ——
它让 `clock` 被**就近塞进最像的那一族**，而且看起来有结论。

> **这才是真正的教训**：指标漏掉一类形态时，系统不会报错，
> 它会**安静地给出一个错误分类**。没有 FAIL、没有异常，只有一张看着挺像的表。

### 47.3 修法：第四类指标 —— 按角度扇区追踪

绕中心切 24 个 15° 扇区，逐帧取"当前变化最集中的扇区"，得到角度轨迹：

```
clock / 本次 random： 75° → 0° → 345° → 330° → ... → 180° → 90°
```

**判据**：`rot_span ≥ 12`（扫过半圈）且 `rot_mono ≥ 0.7`（顺时针单调一致）。
门槛必须两个都卡 —— 只卡 span 的话，"局部纹理零星点亮不同扇区"也会被抓进来。

标定（`tests/test_transition_table.py` 第 8b 组）：
- 合成的顺时针 wheel → `is_rotation=True` ✔
- 直线推进 → `False`（不能污染整页平移族）✔
- 静止 → `False` ✔

### 47.4 附带修正的两条

用户同一次还指出两处，都对：

| 效果 | 我原来写的 | 实际 | 证据 |
| --- | --- | --- | --- |
| `uncover` | 起点在中间、终点最左 | **起点在右缘，变化前结束于中间偏左** | 用【基准帧差】看能量：帧 70 达峰（重心 0.40 居中），之后才衰减到 0.18 |
| `curtains` | `t→b`（上下开合） | **`l↔r`（左右对开）** | 变化重心全程钉在 0.50（0.50/0.46/0.50/0.45/0.51），对称 = 两侧同时开 |

`uncover` 那条我当初**只抽样了靠后的帧**，于是只看到"末尾在左"，把起点也写成了中间。
**教训：判"起点"必须回到第一帧，不能只看轨迹的后半段。**

### 47.5 方法论：每加一类"看的方式"都要问它看不见什么

四个指标覆盖：平移 / 扫描 / 扩散 / 旋转。
每次新增指标时，必须同时问 —— **它看不见什么？** 答案往往就是下一个盲区。

而且**人眼仍不可替代**：这次三个 bug 全是一个没写代码的人看出来的。

<a id="s5"></a>
自动指标保证了"量得对"，但**保证不了"量的维度是对的"**。

## 48. §47 的第二次出现：判"镜像"时单路指标又把 `push` 判成了怪东西

§47 的结论是"每个指标都有一族看不见的东西，而看不见时不报错、只给错答案"。
当时以为那是个关于旋转的教训。**不是** —— 两周后在补 `dir` 缺口时，同一个坑
原样又踩了一次，只是主角从 `clock` 换成了 `push`。

### 48.1 症状：`push` 被自己的判据判成 `ambiguous`

要回答的问题很朴素：**把 `<p:push dir="l"/>` 改成 `dir="r"`，运动是不是镜像？**
这是选择层整张推荐表的地基，此前一直是从属性字面意思推的。

第一版判据只看**变化重心的逐帧轨迹**（`cx_trace`），比较两个方向的相关系数。
结果：

```
push       ambiguous   r=0.565   l 位移 r->l    r 位移 l->r
```

看起来像"push 的镜像行为不成立"。**错的不是 push，是仪器。**

### 48.2 根因：整页平移时变化重心**根本不动**

`push` 是**整页平移** —— 画面的**每一列变化量都相等**。变化重心是"变化量的重心"，
每列一样就等于不动。实测 `dx` 只有 **0.011**，落进 `_profile_metrics` 自己的
"静止"阈值里。

这不是新知识：§47 之前的"坑 3"就记着"整页平移读成 0"。**知道，但还是踩了** ——
因为这次关心的是"两个方向的轨迹像不像"，想当然地拿了最顺手的轨迹指标。

换成**累积位移**（`tx`，逐帧相位相关求和）后：

```
push   dir=l   tx = -1.004
push   dir=r   tx = +1.009      → 反向、距离几乎相等 = 镜像
```

### 48.3 反过来，累积位移也看不见扫描类

那是不是用 `tx` 就够了？不行。`wipe` 是**扫描**（一条前沿扫过），
总质量位移 ≈ 0：

```
wipe   dir=l   tx = +0.003
wipe   dir=r   tx = +0.003      → 两个方向都读不出来
```

而它的变化重心轨迹相关系数是 **r = -0.994**（清清楚楚的镜像）。

**两条路各自看不见一族**：

| 仪器 | 看得见 | 看不见 |
| --- | --- | --- |
| 变化重心 `cx_trace` | 揭示/扫描类（wipe/cover/uncover） | **整页平移（push）** |
| 累积位移 `tx` | 整页平移（push） | **扫描类（wipe）** |

所以判据是**两路并行、取有信号的那路**（`mirror_verdict`），并在结果里标 `via`
（`trace` / `shift` / `both`）—— 让读者知道这个结论是哪只眼睛看见的。

### 48.4 顺带：分析窗口吞掉了整段片子

补测时 `curtains` 被量成 `t→b`，与形态层写的 `l↔r` 冲突，**一度以为是形态层错了**。

查下去是取样窗口的问题：窗口写的是 `bnd-2s .. bnd+3s`，而这批渲染只有 148 帧
（`bnd=60`），于是 `bnd+3*fps = 150 > 148` 且 `bnd-2*fps = 0` —— **窗口覆盖全片**，
把第 1 页的停留也当成过渡的一部分，活跃窗口检测只剩 1 帧。

**修法**：窗口收成 `bnd ± 1.5s`（过渡只有 0.5–1.0 s）。且 `cmd_shapes` 与
`cmd_dirmirror` **同源同修** —— 两层口径不同步，比两层都错更难查。

**教训（比 bug 本身重要）**：数据与既有结论冲突时，
**先怀疑自己的口径，再怀疑那个结论**。回原始帧目视（抽帧拼带）后确认：
`curtains` 是**竖向条带 = 左右对开**，形态层是对的。
如果当时直接"按实测改文档"，就会把对的改成错的。

### 48.5 沉淀

- 判据必须**两路并行**，且结果里记下**是哪路判的**（`via`）。
- 新增任何指标时，除了问"它看得见什么"，还要问 **"它和已有指标的盲区是否互补"**。

<a id="s6"></a>

<a id="s6"></a>
  互补才有资格并进来。

<a id="s6"></a>
- 与既有结论冲突时，**先复核自己的测量口径**，别急着改结论。

## 51. 切换与页内动画**不是正交的** —— 动画要排队等切换演完

### 51.1 症状：挂上切换以后，入场动画像"慢了半拍"

同一页上既写了 `<p:transition>` 又写了 `<p:timing>` 动画，
**两个块都在、PowerPoint 都认、顺序也对**，但放映时：

- 切换（比如 `push` 800 ms）照常演完；
- 然后有一段**什么都不动**的空档；
- 然后入场动画才开始。

看起来像"动画被压缩了"或者"设置丢了"，其实都不是。

### 51.2 根因：文档写的是"正交"，而它只对了一半

`transition-model.md` 早先的版本有三处写了：

> 「页内个体行为走 `<p:timing>`，**与切换正交**、不限名额」

「不限名额」是真的（一页可以挂任意多个动画）。
但「正交」是**从 XML 位置推出来的** —— 推断依据是"两者写在不同的槽位上"。
**位置不同 ≠ 行为独立。** 这正是本项目 §22/§28 反复反对的那类推理。

实测（9 份 deck，每份往返一次）：

| 问题 | 结论 |
| --- | --- |
| 两个块是否都活下来？ | **都活**，`transition` 在前 `timing` 在后，9/9 无一丢失 ✅ |
| 动画什么时候开始？ | **切换演完之后** —— 延迟 ≈ 切换时长 + 133 ms ❌ 推翻了"正交" |

| 同页的切换 | 动画开始（相对页边界） |
| --- | --- |
| 无（硬切） | +67 ms |
| `fade` 300 ms | +433 ms |
| `push` 800 ms | +933 ms |
| `wipe` 800 ms | +933 ms |
| `fade` 1500 ms | +1633 ms |

而动画**自己的长度一点没变**：五种组合下淡入斜坡都是 14 帧 ≈ 467 ms
（写入的 `dur="500"`）。**切换改的是动画的起点，不是动画的长度。**

### 51.3 ⚠️ 本次测量里最值钱的一条：通用能量指标对"淡入"是全盲的

第一版用逐帧能量（`_profile_metrics` 那套）去判"动画有没有跑"，结果：

```
timing_solo_anim    centre runs = 0    full runs = 0
```

**读起来像"动画根本没跑"。** 它跑了 —— 只是中灰圆盘淡入到中灰网格上，
整帧均值变化小于 2/255，落在任何合理阈值之下。

改用**第三路仪器**：让两页的标记圆盘用不同色相（第 1 页红、第 2 页蓝），
"新页的形状出现了没有"于是变成直接的颜色测量 `max(0, B − R)` 的和。
一眼就看见 14 帧的线性斜坡。

**这是同一个坑的第三次出现**：§47（旋转躲过三类指标）、§48（整页平移躲过重心）、
现在是淡入躲过能量阈值。**每加一类"看的方式"都要问它看不见什么。**

### 51.4 判据

```
timingdeck <dir>                              # 9 份 deck（组合 + 各自对照）
probe_shapes.ps1 -Dir <dir>                   # 逐份渲染
probe_timing_roundtrip.ps1 -Dir <dir>         # 结构：两块是否都活
timingdiff <dir> --out j.json --png chart.png # 时间：进入形状何时出现
```

**对照组必须换同一个切换。** 第一版把 `solo_trans` 写成 `<p:fade/>`、
把 `both_push` 写成 `<p:push/>`，于是"组合 vs 单独"一次动了两个变量，
低能量的 fade 被读成"切换消失了"。**组合行与对照行之间只能差一个变量。**

### 51.5 沉淀

- **结构平行 ≠ 时间平行。** 两个块都能装，不等于两个块同时演。
- 页内动画的 `trigger: with` 里的 "with" 是"与**本页动画序列**的第一项同时"，
  **不是"与切换同时"** —— 切换根本不在那个序列里。
- 想要"翻页过程中就有东西在动"，只能用**切换本身**（整页位移／方向揭示），
  或者用 morph 把运动设计在**页间**；页内动画拿不到切换那段时间。
- 一页的时间总占用 ≈ **切换时长 + 页内动画总时长**。
  `motion-design-spec` §6 的时长上限判据原本只看动画，**漏算了切换** ——
  1.5 s 的切换后面挂一串入场动画，观众要等 1.5 s 才看见第一个元素。
- **对照实验一次只动一个变量**；判"有没有动"的仪器选错，会得到"什么都没发生"这种
  看起来最像结论的错误答案。
