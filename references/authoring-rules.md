# motion spec 编写约束（这些规则是被 bug 换来的）

本文每一条都对应一次**真实翻车**：动画注入成功、`geometry: UNCHANGED` 通过、
`verify_motion` 通过，但**用户一看就发现不对**。所以它们是硬约束，不是建议。

判定标准很关键：**"注入没报错" 不等于 "动效是对的"**。上面那几个门禁只证明
OOXML 合法、几何没动，**证明不了"该动的都动了、顺序对、单位对"**。
下面 13 条专治门禁管不到的那一类。

---

## A. 目标锚定：不要手写 id

### A1. spec 必须由实测几何生成，禁止手写形状 id 列表

**翻车**：deck 改一次版式，形状 id 就全体重排。手写的 spec 于是指向了**别的形状**——
不是报错，是静默错位：

| 页 | spec 写的 | 实际是 | 后果 |
| --- | --- | --- | --- |
| P6 第三张卡 | `id=17,18,19,21,22,23` | `id=19,20,21,22,23,24` | 整张卡没动画，且**正好差一位**，极其难看出来 |
| P4 美国列 | — | 24 个形状 | 整列没有动画 |
| P7 右栏 | — | 8 个形状 | 整栏没有动画 |
| P8 映射表 | — | 45 个形状 | 整表只有一次整页淡入 |

**约束**：写一个"读实际 deck 形状 → 按几何分组 → 生成 spec"的脚本
（见 `references/template-patterns.md` 的分组方法）。id 只能来自运行时读取。

### A2. 必须显式断言"每个形状都有效果"

**为什么**：这不是一个明显问题，因为**没有动画的形状在放映开始那一刻就是可见的**。
它不会消失，只会"一直在那儿"——用户的描述是"这一列一直出现，不随动画变化"。
门禁全绿，因为什么都不缺。

**约束**：生成 spec 时断言 `所有形状 - 页脚 - 已覆盖 == 空集`，否则构建失败。
页脚（署名 + 页码）是有意静态的，用白名单排除；白名单要作为参数传进去，
不要把某个项目的页脚文案写死在工具里。

### A3. 一个形状只能有一个效果，且必须显式检查

`com-pitfalls.md` §14：同一形状上"入场 + 强调"会被 PowerPoint 静默丢弃。
另外，重复效果本身也说明分组逻辑出了问题。生成时断言 target 不重复。

## B. 单位：本项目最容易翻车的地方

### B1. 三种单位不许混用：EMU / point / inch

`1 pt = 12700 EMU`；本 deck 是 **960×540 pt**；`1 in = 72 pt`。

**翻车记录**（同一天内犯了三次）：

| 写的 | 实际含义 | 后果 |
| --- | --- | --- |
| `sh["pt"][3] > 1.0` | 1.0 **pt**，不是 1 英寸 | 卡片检测条件恒真/恒假，分组全错 |
| `4.0 < y < 4.9` | y 是 **pt**（332），不是英寸（4.62） | 三张卡片一个都没匹配上 |
| 容差 `0.1` | 0.1 **pt** | 容差形同虚设，幻灯片标题被吞进卡片分组 |

**约束**：
- `player.shape_index()` / `motion.inspect()` 返回的坐标是 **point**；
- `_patch_*` / `build_deck` 里画形状用的是 **inch**；
- 任何比较之前先想清楚两边是什么单位。跨单位比较一律显式换算。

### B2. id 的类型要统一

`player.shape_index()` 从 XML 正则里取 id，返回的是 **字符串**。
和 int 混在一起会：

- `sorted()` 直接抛 `TypeError: '<' not supported between instances of 'str' and 'int'`；
- 更早、更隐蔽的是 `"2" in {2, 3}` 恒为 `False`，于是"取反"逻辑全部失效。

**约束**：在读取边界统一 `int()` 一次，不要在每个调用点各转一次。

## C. 分组：按"视觉单元"聚类，不要按精确值

### C1. 表格按**垂直中心**聚类，不要按顶边精确相等

**翻车**：我按"顶边相等"给表格分行。但一行的**标签文字比它的单元格底色低约 12pt**，
内容文字又低几点。结果**每一行被拆成三个独立"行"**，揭示顺序变成
`表头 → 内容 → 自己的标题` —— 用户的原话是"左侧的标题比右侧内容出现晚"。

**约束**：按 `y + h/2` 聚类，容差取"行间距"和"标签偏移量"之间：
本 deck 行间距约 40pt、标签偏移约 4pt，所以取 **25pt**。
容差太小 → 一行拆多行；太大 → 相邻行粘连。

### C2. 分组要给"整个视觉单元"，不是零散形状

一行 = 标签底色 + 标签文字 + 两列单元格底色 + 两列文字 + 分隔线。
分组时要一起抓进来，且**按 x 排序**决定揭示次序（最左的标签先出）。

## D. 顺序：z 序 ≠ 阅读序 ≠ 动画序

### D1. 底部结论条必须**最后**出现

**翻车**：P7 的结论条是"整宽的浅橙块"，它的**顶边比左右两栏的底边还高**。
所以按 y 排序时，它排到了右栏**前面** —— 结论比论据先出现。

**约束**：整页级的收束条/强调条一律从自动排序里排除，**显式追加到 effects 末尾**。

### D2. 别用"位置排序"推断阅读顺序

`spTree` 顺序是**绘制顺序**（z 序），不是阅读顺序。要按阅读序就按 (y, x) 排，
并且**心里过一遍排出来的结果**，不要假设排序结果就是你要的。

### D3. 顺序类 bug 只能靠"打印出来看"

`geometry: UNCHANGED` / `verify_motion` 都不会报顺序错。生成 spec 之后
**把 target → 文本 的列表打出来读一遍**。这次三个顺序 bug 都是这么发现的。

## E. 版面：文字必须真的在框里

### E1. 文字框的 y 要落在它所属的色块区间内

**翻车**：统一各页底部条位置时，条改到了 `y=6.34`，但 P7 的**文字还留在 `y=5.94`**——
文字浮在框**上方** 0.4 英寸。用户看到的是"下方文字不在框内"。

**约束**：改任何色块的 y/高度时，**同一次编辑里**改掉它内部所有文字的 y。
改完用 `check_layout.py` 的"文字是否落在容器内"这一条兜底。

### E2. 文本框宽度必须用实际字体量过，别估算

用 PIL 加载真实字体（`msyh.ttc` / `consola.ttf`）量 `font.getlength()`，
按宽度贪心换行算行数。本 deck 的两次翻车：

- P3 时间轴节点说明用了太长的一行，**"装"字单独掉到第四行**；
- P6 卡片正文框**右边距只有 0.14in（左边 0.28in）**，加上 `· ` 前缀后
  引号被孤立到第二行。

**约束**：
- 有 `\n` 的文本，每一行都要量过；
- 文本框内边距**左右对称**（别一边 0.28 一边 0.14）；
- 容器内文字的总高度 ≤ 容器高度，否则断言失败。

## F. 校验器本身也会骗你——先校准再信它

**翻车**：我加的 `check_layout.py` 撞页脚规则，第一版把**页脚自己**、
**全出血背景**、以及**只有 0.03in 余量的正常情况**全报成了问题（23 条）。
如果当时信它，就会去"修"三个本来正确的东西。

**约束**：
- 校验规则要先解释清楚"什么才算违规"，并给出**豁免条件**
  （页脚自身、全出血背景、以及可接受的余量）；
- 一条规则报出大量问题时，**先怀疑规则**，不要先改版面；
- 规则改完要**能抓回它本来要抓的那个 bug**（这里是 P8/P9 底条压页脚），
  否则它已经退化成噪声。

## G. 一次改动的正确收尾顺序

deck 一改，id 就可能重排。所以**改完版面必须重跑全链**，顺序不能省：

```
1. 生成图表素材        make_assets.py
2. 构建 deck           build_deck.py        <- 会重排 id
3. 重新生成 spec       make_motion.py       <- 必须重新读 id
4. 覆盖率 + 目标 + 版面  check_coverage / check_motion / check_layout
5. 注入 + 几何自证      motion.py apply --assert-geometry
6. 结构自证            verify_motion.py --source
7. PowerPoint 往返     motion.ps1 -Strict
8. 重建动效预览         motion.py player
```

**第 3 步最容易被跳过**：只改了版面、觉得"spec 没动"就直接复用旧 spec，
于是 id 静默错位——这正是 P6 那个 bug 的成因。

- [ ] 确认每个列表/表格是**逐项揭示**，不是一次到位
- [ ] 确认**标题在内容之前**、**结论在论据之后**
- [ ] 确认没有"浮在框外"的文字
- [ ] 确认同类型卡片**样式一致**（高度、徽标颜色、顶条颜色）
- [ ] 面向**听众**读一遍文案：非专业听众能不能听懂（技术页尤其）
- [ ] **如果 spec 用了 `dir:`，亲眼看一次方向**。`wipe(left)` 与 `wipe(right)` 的
      `presetID/presetClass/presetSubtype` 完全相同，只差 `filter` 字符串，所以
      `--assert-geometry`、`verify_motion`、往返普查三个闸**都看不出方向装反了**。
      本机也无法自动校准：见下方 §I 的三条死路。看一条横向擦除的线/条，一眼就能判定。

## I. `dir:`（方向性擦除）——能力与它的验证边界

### I1. 用法

spec 里给**带 filter 的效果**加 `dir:`，取值
`down left right up upleft upright downleft downright`：

```yaml
- {target: 24, effect: wipe, duration: 1.6, dir: left}   # 线从左往右画出来
- {target: 41, effect: wipe, duration: 0.9, delay: 0.3, dir: down}
```

只有**有方向的 filter** 才接受它：`wipe / barn / checkerboard / circle / diamond /
plus / wheel / wedge / strips`。给 `fade`、`fly`、动作路径写 `dir:` 会**直接报错退出**，
而不是静默忽略——静默忽略的后果是"动画不是你要的那个"，而三个结构闸都发现不了。

`dir` 在 spec 里是**逐效果覆盖**，不是单独的 alias：`wipe(left)` 不是独立的
presetID，方向只存在于 `<p:animEffect filter="...">` 的取值里。

### I2. 它买到什么

- 横向的线/条用 `dir: left` 才是"被画出来"；默认的 `wipe(down)` 会读成"掉下来"。
- 数据条从左到右填充 = 时间在推进；同一批形状改成上下展开就完全没有这个含义。
- 一页里**同一个效果因为方向不同而表达不同意思**，这是 spec 层面唯一能做到的手段。

### I3. 为什么方向在本机无法自动验证（三条死路，别重走）

想把方向测出来，必须看到动画的**中间态**。本机三条路全部不通：

| 探针 | 结果 |
| --- | --- |
| `SlideShowView.Export` | 这个 build **根本没有这个成员**，报 `<unknown>.Export` |
| `Slide.Export` / `Shape.Export` | 导出的是**终态**，完全无视实时可见性与 filter 状态。实测：6 秒的 wipe 在 2.4 秒采样，八个方向**全部 100% 不透明** |
| 截屏（`ImageGrab` / `PrintWindow`） | 需要桌面真的在渲染。实测抓到的画面 97% 接近纯黑、只有 0.55% 亮于灰 200，即屏幕没有输出（休眠/锁定）。`PrintWindow(PW_RENDERFULLCONTENT)` 返回的是**桌面 DC**，不是窗口自身内容 |

所以：`player.py` 的 `WIPE_CLIP` 按文档约定映射，在代码里**明确标注为未在本机验证**，
并靠 §H 那一条人眼检查兜底。`showcase/qa/calib_wipe.py` 只验证能得到证的部分：
`dir` 确实写进了 `filter=`、几何字节不变、以及"给无方向效果写 dir 会报错"。

### I4. `player` 必须跟着做方向

只让 OOXML 带方向是不够的：`player` 是**唯一能看见动效的地方**，如果它把所有擦除都
渲染成"从左边长出来"，那它验证的就是错的东西。所以 `player.py` 里有一张
`WIPE_CLIP`（八个方向的 CSS `inset()` 起始状态）。

## J. 那个"同一个形状上多个效果"的坑，Round-trip 会以另一种方式咬你

§A3 说了一个形状只能有一个效果，理由是"入场+强调"会被 PowerPoint 丢掉。
还有**第二种**表现，成因不同、症状相似，容易误诊：

**逐段揭示**（by-paragraph build）在 PowerPoint 里就是"同一形状挂多个效果"。你写进
spec，`motion.py apply` 会老老实实写成 5 个 `<p:par>`，`--assert-geometry` 通过、
`verify_motion` 通过、`motion.py check` 也通过——然后 `motion.ps1 -Strict` 的往返普查
报 **`LOSS`**：

```
round-trip census: 153 effect(s) written back, 155 were in the input
```

**实测**：两个逐段块，每个多一个效果，正好丢 2 个。PowerPoint 重新读时间轴时把重复
形状折叠成一行，多出来的效果被丢掉。

**正确做法**：不要靠"一个框多段"来做逐行揭示，改成**一行一个文本框**。每个文本框是
独立的 shape id，各自只有一个效果，什么都不会被折叠；版面看起来一模一样。

```python
# 错的：一个框两段，spec 里必须给同一 id 写两个效果
text(sl, x, y, w, h, [("第一行", 16, ...), ("第二行", 16, ...)])

# 对的：一行一个框，各自独立
for i, (line, y) in enumerate([("第一行", y0), ("第二行", y0 + pitch)]):
    text(sl, x, y, w, h, [(line, 16, ...)])
```

判断方法：`LOSS` 的数字**正好等于"逐段块数 × (段数-1)"**，而不是任意数字。
看到这个规律就别去查"入场+强调"了。
