# 3D 相机与旋转:参数 → **实测**结果

这份文档的每一个数都是**在这台机器上渲染出来量到的**,不是从规范抄的。
`scripts/camera_reference.json` 是同一份数据的机器可读版;
`scripts/build_camera_table.py` 是可重跑的测量脚本。

---

## 1. 为什么要有这份表

本轮做"立体版"效果时,同一类问题反复出现:**参数被接受 ≠ 参数有效 ≠ 结果如你所想。**
实测到四种脱节:

| 类型 | 实例 |
| --- | --- |
| 参数变了,**结果没变** | 五个透视预设渲染完全相同;`PresetThreeDFormat` 接受值但投影不变 |
| **名字和语义相反** | `Perspective = 0` 与 `= 1` 都是"平行",`-1` 才是"透视" |
| **两套参数轴不对应** | 窗格 `RotationX/Y` ≠ OOXML `lat/lon` |
| **值域越界不是忽略,是拒绝** | `lat=21600000`(规范给的上界)让**整个文件损坏** |

**所以:参数要当"待测对象",不是"待查文档"。** 先扫、渲染、量一个可量化特征,再建表。

## 2. `camera` 元素结构(ECMA-376)

```xml
<a:scene3d>
  <a:camera prst="perspectiveFront" fov="5400000" zoom="100000">
    <a:rot lat="18600000" lon="0" rev="0"/>
  </a:camera>
  <a:lightRig rig="threePt" dir="t"/>
</a:scene3d>
```

| 属性 | 类型 | 规范值域 | **实测可接受** |
| --- | --- | --- | --- |
| `prst` | `ST_PresetCameraType` | 62 个枚举名 | ✅ 全部可用,见 §3 |
| `fov` | `ST_FOVAngle` | 0 ~ 180°(1/60000 度) | ✅ 0 ~ **10800000**,与规范一致 |
| `zoom` | `ST_PositivePercentage` | 1/1000 百分比,默认 100000 | ⚠️ **不做范围校验**,连 `2147483647` 都收 |
| `lat` / `lon` / `rev` | `CT_SphereCoords` | **0 ~ 21600000** | ❌ **实为 0 ~ 21599999** |

### ⚠️ 规范的上界会毁文件

**`lat` / `lon` / `rev` 写 `21600000`(规范明写的合法上界)时,
PowerPoint 报 `0x80070570` —— 文件或目录损坏且无法读取。**

**真实上界是 `21599999`。** 三个属性都实测过,行为一致。

```python
def norm(deg):
    """角度 -> OOXML 安全值。务必归一化,负数和大值都会毁文件。"""
    v = int(round(deg * 60000)) % 21600000
    return v if v < 21600000 else 21599999
```

`0x80070570` 这个错误码在 OOXML 注入里**几乎总是指"属性值越界或结构非法"**,
不是文件真的坏。遇到它先查数值范围。

## 3. 62 个预设:名字决定**投影类别**

`MsoPresetCamera`(`Microsoft.Office.Core`,1~62)的官方名称,全部实测。
标题列的**收敛比**是判据:**1.000 = 平行投影**,**明显小于 1 = 真透视**。

| 枚举 | 预设 | 类别 | 收敛比 |
| --- | --- | --- | --- |
| 1–9 | `legacyOblique*` | 平行 | ~1.000 |
| 10–18 | `legacyPerspective*` | **透视** | 0.74 |
| 19 | `orthographicFront` | 平行 | 1.000 |
| 20–39 | `isometric*` | 平行 | ~1.000 |
| 40–47 | `oblique*` | 平行 | ~1.000 |
| 48–60 | `perspective*` | **透视** | 0.92 |
| 59–60 | `perspectiveHeroicExtreme*` | **透视(更强)** | 0.84 |
| 61–62 | `perspectiveRelaxed*` | **透视** | 0.92 |

### 三条能省下大量试错的结论

1. **只有 `perspective*` 和 `legacyPerspective*` 两组会产生透视。**
   其余 47 个(oblique / isometric / orthographic)**全是平行投影,永远没有灭点**。

2. **"适度宽松"(`perspectiveRelaxedModerately`)和"宽松"(`perspectiveRelaxed`)
   渲染完全相同**(都是 0.917)。选哪个都行,别指望它们有区别。

3. **预设内部差异极小。** 48–58 那十一个预设实测**收敛比完全一致(0.917)**。
   原因是:一旦显式写了 `lat`,**`lat` 会覆盖预设自带的角度**,
   于是预设只剩下"平行还是透视"这一位信息起作用。

   > 换句话说:**预设选类别,角度靠 `lat/lon`。**

## 4. `lat` / `lon` 各管什么

在 `perspectiveFront` 上扫 `lat × lon`:

| lat | lon | 收敛比 | 压扁度 | 说明 |
| --- | --- | --- | --- | --- |
| 330° | 0° | 0.944 | 0.483 | 轻微俯视 |
| **315°** | **0°** | **0.928** | **0.394** | **推荐:俯角够,不压扁** |
| 300° | 0° | 0.907 | 0.280 | 更俯,更扁 |
| 285° | 0° | 0.901 | 0.144 | 近乎水平,极扁 |
| 330° | 30° | 0.837 | 0.844 | 侧转 |
| 330° | 60° | 0.857 | 1.816 | 大侧转,板竖起来 |
| 300° | 60° | 1.273 | 5.415 | **超出量测有效范围** |

### 结论

- **`lon = 0` 时形状最规整**(纯正视图,左右对称)。做"躺平的地面"就用 `lon = 0`。
- **`lat` 主要控制压扁度**(0.483 → 0.144),数值越小板越扁。
- **`lon` 是非零时开始侧转**,`lon ≥ 30°` 后压扁度急剧上升、形状明显不对称。
- **`lon = 60°` 且 `lat ≤ 300°` 的那些行不要用**:形状严重畸变,
  收敛比甚至 `> 1`,说明它已经不是一块可读的平面了。

## 5. `fov` 是**透视强度的连续旋钮**

| `fov` | 收敛比 | 压扁度 |
| --- | --- | --- |
| 0° | 1.000 | 0.356 |
| 15° | 0.977 | 0.356 |
| 45° | 0.917 | 0.358 |
| 90° | 0.814 | 0.359 |
| 120° | 0.695 | 0.362 |
| **150°** | **0.438** | 0.358 |

- **单调、可预测**,而且**几乎不影响压扁度** —— 也就是说
  **`fov` 单独控制"透视有多强",`lat` 控制"俯角有多斜",两者可分别调。**
- `fov = 0` 时收敛比 1.000,**等价于平行投影**。
- **规范说 `fov` 对非透视相机被忽略,实测确认**(`orthographicFront` 下任何 fov 都是 1.000)。

> **这条和 [MS-OI29500] 的说法要对一下**:那份实现说明写的是
> "`fov` 对**非透视**相机被忽略" —— 实测一致。
> 但网上常见的转述会写成"`fov` 被忽略",那会让人以为它没用,
> **实际上它在透视相机上是最好用的那个旋钮。**

## 6. `zoom` 不影响透视,只缩放

| `zoom` | 收敛比 | 压扁度 |
| --- | --- | --- |
| 25000 | 0.911 | 0.360 |
| 50000 | 0.922 | 0.351 |
| 100000(默认) | 0.917 | 0.358 |
| 200000 | 0.917 | 0.361 |

**`zoom` 不改变投影几何**,收敛比在 0.911~0.922 之间波动(量测噪声)。
它是沿视线方向的缩放,`zoom` 越大画面里物体越大。

**但要注意**:`zoom` 放大到一定程度,形状会**超出画面**,
此时任何基于剪影的量测都失效(见 §7)。

## 7. ⚠️ 量测的有效范围(这条比数字本身重要)

**剪影一旦触及画面边缘,量出来的就不是形状,是画面边界。**

这个坑我踩过并已修正:`zoom = 200000` 时最初量到收敛比 **1.000**,
看起来像"zoom 把投影变成平行"。实际是**板子放大到出画**,`near_w == far_w == 图像宽`。
**同样的假象当时静默污染了整个 `fov` 扫描**(`fov ≥ 120` 的 `near_w` 全部触顶到 1200)。

**所以测量脚本现在会检测剪影是否接触边缘,接触就标记 `clipped: true`
并拒绝给出收敛比**,而不是输出一个无意义的数字。

**读表时的容差**:理想平行投影的收敛比是 1.000,但像素级量测有噪声,
实测正交相机落在 **0.90~1.00**。**判据是"接近 1"而不是"等于 1"。**

## 8. 怎么用这张表

**要做"躺平的地面"(参考图那个效果):**

```xml
<a:camera prst="perspectiveFront" fov="5400000">   <!-- fov 90°,透视中等 -->
  <a:rot lat="18900000" lon="0" rev="0"/>          <!-- lat 315°,俯角 -45° -->
</a:camera>
```

- `prst` 必须选 `perspective*` 或 `legacyPerspective*`,否则**永远出不来透视**
- `lat = 315°`,**不要写 `-45°`**(负数毁文件)
- `lon = 0`,保持正视图对称
- 想要**透视更强**就加大 `fov`,不要靠 `lat` 硬压(那会连带压扁)

**要判断"躺下了没有":量远边是不是明显比近边窄。**
不要看"像不像平行四边形" —— **平行投影的矩形在任何角度都像平行四边形**,
这个判据零区分力,我因此选错过一次姿态。
